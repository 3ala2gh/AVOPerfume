## Project overview

AVO Perfume is an e-commerce site (live at https://avo-perfumes.netlify.app/) with two independent apps in this repo:

- `backend/` — NestJS + Prisma (PostgreSQL/Supabase) REST API, global prefix `/api`.
- `frontend/` — React + TypeScript + Vite storefront and admin dashboard.

There is no monorepo tool (no workspaces/turborepo) — each app has its own `package.json`, `node_modules`, and is run/built independently.

## Commands

### Backend (`backend/`)
```bash
npm run start:dev        # watch-mode dev server (port 3000, or $PORT)
npm run build             # nest build
npm run start:prod        # run compiled dist/src/main.js
npm run lint               # eslint --fix over src/apps/libs/test
npm run test                # jest unit tests
npm run test:e2e            # jest e2e (test/jest-e2e.json)
npm run test -- <pattern>   # run a single test file/suite by name pattern
npm run prisma:generate     # regenerate Prisma client after schema changes
npm run prisma:migrate:dev  # create+apply a migration in dev
npx prisma migrate deploy   # apply pending migrations without dev prompts (use for staging/prod DBs)
npm run prisma:seed         # run prisma/seed.ts
npm run prisma:studio       # open Prisma Studio
```
Note: there are currently no `*.spec.ts` files in `src/`, despite the jest scripts being wired up.

Requires a `backend/.env` (gitignored) with at least: `DATABASE_URL`, `DIRECT_URL` (Prisma needs both — see `prisma.config.ts`, which uses `DIRECT_URL` for CLI/migration workflows), `JWT_SECRET` (`JWT_EXPIRES_IN` optional, defaults to `7d`), `CLOUDINARY_CLOUD_NAME`/`CLOUDINARY_API_KEY`/`CLOUDINARY_API_SECRET` (image uploads), and `FRONTEND_DEPLOY_HOOK_URL` (used by the "Publish website" admin action).

### Frontend (`frontend/`)
```bash
npm run dev            # Vite dev server (port 5173), reads live backend via VITE_API_BASE_URL (defaults to http://localhost:3000/api)
npm run generate:data  # fetch backend data and bake it into public/data/{products,categories,offers}.json
npm run build           # runs generate:data, then tsc -b, then vite build — build fails if the backend isn't reachable
npm run lint             # eslint .
```
No test runner is configured for the frontend.

## Architecture

### Static-data publish pipeline (read this before touching product/category/offer data)
The public storefront **never calls the live backend directly** — it reads static JSON files (`frontend/public/data/{products,categories,offers}.json`) via `frontend/src/api/public-data.api.ts`, falling back to the live API only if the static fetch fails. Those JSON files are generated by `frontend/scripts/generate-static-data.mjs`, which is wired into `npm run build` (`generate:data && tsc -b && vite build`). The admin's "Publish website" button (`AdminDashboardPage` → `usePublishWebsiteMutation` → `POST /admin/publish-website` → `AdminService.publishWebsite()`) simply pings `FRONTEND_DEPLOY_HOOK_URL`, a deploy-platform webhook that triggers `npm run build` on the hosting platform, which regenerates those JSON snapshots from the current DB state.

Practical implication: any product/category/offer change made through the admin API is saved to the DB immediately, but **shoppers only see it after the next "Publish website" click** (or any redeploy that reruns `npm run build`). The admin dashboard itself always reads live from the backend (`useProductsQuery({ source: 'admin' })` → `listProductsFromApi`), while every public-facing page uses the static-JSON path (`useProductsQuery({ source: 'public' })`, the default, → `listPublicProducts`).

Three+ places reshape the API's `sizes[]`/price fields with their own hardcoded logic and must be kept in sync whenever a new per-size field is added:
1. `frontend/scripts/generate-static-data.mjs` (`normalizeProduct`) — bakes into `products.json`
2. `frontend/src/api/public-data.api.ts` (`normalizeProduct`) — runtime read of the static JSON + live fallback
3. `frontend/src/components/home/catalogData.ts` (`normalizeProductSizes`) — `Product` → `Perfume` conversion used by every storefront page
4. `frontend/src/api/products.api.ts` (`listProductsFromApi`) — admin's live product list

### Perfume sizes are fixed columns, not a variants table
`Perfume` (see `backend/prisma/models/perfume.prisma`) has no separate size/variant table. Each of the 4 fixed sizes (10ml/30ml/55ml/100ml) is its own set of columns (`price10Ml`, `is10MlEnabled`, etc.). `backend/src/modules/products/mappers/perfume.mapper.ts` (`mapPerfume`) is the single place that assembles these flat columns into the `sizes: [{ size, price, originalPrice, enabled }]` array shape consumed by the frontend — any new per-size behavior needs a column here, a DTO field in `backend/src/modules/products/dto/perfume.dto.ts` (shared base class extended by `CreatePerfumeDto`/`UpdatePerfumeDto`), and a mapper entry, in addition to the frontend reshaping points listed above.

### Backend module layout
- `common/auth/` — `AuthTokenService` (JWT sign/verify), `AdminJwtGuard` (checks `role === 'admin'` from the JWT payload, no DB lookup), `PasswordService` (bcrypt).
- `common/prisma/` — `PrismaService` extends the generated `PrismaClient` using `@prisma/adapter-pg`, constructed from `DATABASE_URL` directly (not through `prisma.config.ts`, which is CLI-only).
- `common/cloudinary/` — image upload wrapper used for perfume/offer images.
- `modules/auth/` — email/password login and registration against the `User`/`Role` Prisma models (roles: `admin`, `user`).
- `modules/products/` — perfumes, categories, and offers; all admin-mutating routes on `ProductsController` are behind `AdminJwtGuard`; `GET` routes are public.
- `modules/admin/` — cross-cutting admin actions that aren't per-entity CRUD: bulk discount application, best-seller ranking, and the static-site publish trigger.

Prisma schema is split into `backend/prisma/models/*.prisma` and composed via `backend/prisma/schema.prisma`; add new models/fields in the relevant `models/*.prisma` file, then create a migration under `backend/prisma/migrations/` following the existing `<timestamp>_<description>` naming convention.

### Frontend structure
- `src/api/` — one file per backend resource area plus `public-data.api.ts` (the static-JSON-first storefront read path) and `api.ts` (axios instance, attaches the admin JWT from `localStorage` under `avo_admin_token` to every request).
- `src/hooks/` — TanStack Query wrappers; query hooks take a `source: 'public' | 'admin'` option where the distinction from the static-data pipeline matters (see `useProductsQuery`, `useCategoriesQuery`).
- `src/components/home/catalogData.ts` — the domain-shaping layer between the raw `Product` API type and the `Perfume` view-model type used across storefront pages/components; also owns size-list constants (`PERFUME_SIZE_OPTIONS`, `DEFAULT_PERFUME_SIZE`) and price/enabled lookup helpers.
- `src/pages/admin/` + `src/components/admin/` — the authenticated dashboard (perfume CRUD, categories, offers, discounts, best sellers, publish trigger); route-gated in `src/router/index.tsx` via `useAdminSession`.
- `src/i18n.tsx` — hand-rolled i18n with English/Arabic string tables; add new UI strings to both language blocks.
